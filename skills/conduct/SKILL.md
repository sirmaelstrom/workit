# Conduct — take a stated goal end to end

`/conduct "<goal>" --repo <abs path to a git checkout>` runs a goal from intent to a merged, analyzed result: it specs the goal, splits it into work packages (WPs), builds each in its own lane, reviews and merges each PR, runs the release recipe if the repo declares one, and writes a run analysis. The operator is asked twice: **touch 1** before `/spec` runs (what authority the run has) and **touch 2** at the showcase (accept, accept with notes, or send back). A third touch, the blocked stop, opens only when a fork can't be settled from evidence.

You drive a one-shot state machine, `${CLAUDE_SKILL_DIR}/scripts/conduct.mjs`. Each verb reads `state.json`, does one bounded thing, writes state and exits. The conductor is you, repeating **intake → next → perform → record**; the run's state is the files under its run dir, not your context, so a rotated conductor resumes from it (§ Rotating the conductor).

```
/conduct "<goal>" --repo <abs path>
         --backend t3|herdr|exec      # where lanes run (§ Where lanes run); t3 when you run in T3 Code
         [--t3-project <id>]          # t3: the T3 project whose workspace root is --repo
         [--backend-why "<reason>"]   # herdr: why T3 won't do (required)
         [--anchor <quest id>]        # Spine adapter: the goal's quest
         [--budget <usd>]             # proposed in touch 1; default 25
         [--lanes <1-4>]              # concurrent lanes per repo; default 2; a 3rd or 4th lane starts only with ≥ 10 GB free commit memory (lane.mjs admit)
         [--agent claude|codex]       # lane agent; default claude on t3, else the first CLI found
         [--adapter <name>]...        # declare spine | council | kb | verify | ledger
         [--no-adapter <name>]...     # force the core path for an adapter
         [--release <json file>]      # a release recipe; else the repo config's release (§ Repo config)
         [--runs-root <dir>]          # where the run dir goes
/conduct --resume <run dir>           # continue a run
```

**One work package by hand.** Asked to execute a single WP from a spec outside a run ("execute WP-01", "run wp"), follow `${CLAUDE_SKILL_DIR}/reference/execute-wp.md` instead of the state machine: it reads the orchestrator and progress log, roots the target, builds the WP and appends its progress entry.

## The loop

Recovery commands and amendment evidence rules: [RECOVERY.md](RECOVERY.md).
Long-running drivers should use `${CLAUDE_PLUGIN_ROOT}/scripts/conduct-run.mjs`
so each invocation follows the run's recorded plugin root after an upgrade.

1. **Start.** Run `node "${CLAUDE_SKILL_DIR}/scripts/conduct.mjs" intake --goal "<goal>" --repo <abs> …` with the flags above (declare adapters first, § Adapters). It prints `{ ok, runDir, action }`. On the core path the first action is touch 1, a `touch`. With the Spine adapter the first action reads the anchor quest, and touch 1 follows as a session ask or, with no operator, a `needs_input` receipt and a hand-back (step 2, `touch`). Exit 2 is a refusal (§ Refusals) and writes nothing.
2. **Perform the action.** Every action has an `id`, a `kind`, an `instruction` a person could follow, and an `expects` field. What you do depends on `kind`:
   - `shell`: run its `command` argv exactly as given, from `cwd` and with `env` added when present. Record `{ "code": <exit>, "stdout": "…", "stderr": "…" }`. `background: true` marks a command that can outlast a foreground shell (a repo's long gate suite): start it in the background, wait for it to exit, and record the same result. The `lane`, `land` and `analyze` verbs (`lane spawn`, `lane check`, `land gate`, `land merged`, `analyze`) reach you only this way: `next` never runs a program, so every check is a `shell` action whose printed result you record. `land gate` exits 6 while CI is still running or a pipeline review of the head is in flight; that is a wait.
   - `agent-tool`: call the named MCP `tool` with `args` and record its raw JSON result. These are emitted only for an adapter that is on.
   - `skill`: invoke the named skill with `skillArgv`, one argument per element (`skillArgs` is its display form), **from the target repo's root** (cwd = the run's `--repo`): `/spec` takes its project from the cwd and doesn't ask. On a greenfield run (`intent.greenfield.on`, § Greenfield bootstrap), the `/spec` action's `skillArgv` ends with `--greenfield`. `/spec` then attacks D1, the stack decision, with one lens before ruling it, and runs core-loop spikes only when the lens names a credible alternative (`${CLAUDE_PLUGIN_ROOT}/reference/patterns/stack-attack.md`, quest 061b526a). For `/spec`, record the JSON the action's `instruction` describes, composed from its report: `depth`, `workshopDir`, `reviewLevel`, and the `gateCommand` (depth `none` or `lite`). A deep run's WPs come from `work-packages/` in the workshop, not from the record. `expects.fields` lists only the minimum. Under the pre-approval no gate shows the spec's `[ASSUMPTION: …]` flags to a person: read the `**Assumptions:**` line of `/spec`'s final output and carry those flags into the showcase by naming them when you present it.
   - `author`: write the file at `outPath`: from `template` with the `slots` filled, or as the instruction describes (the grant at `touches/1-grant.json` from the operator's (c) text, a ruling at `rulings/<wp>-<n>.json` for a lane's question, a lane brief, an amendment). Record `{}`. A `ratify` action comes when a WP is held only because its post-cap tail touches paths outside its Files (inside the line cap). Write `{ "ratify": true, "why": "…" }` to add those paths to its Files and send it back to the gate, so its deferred dependents follow. Write `{ "ratify": false, "why": "…" }` to keep it held. The build doesn't end while that ruling is owed. A `cite` action comes when a WP is held only because its tail has commits no `fixed` row of the latest review cites. Write `{ "cite": { "<sha>": "<comment id>", … }, "why": "…" }`, citing every listed commit on the fixed row whose fix it completes; the WP goes back to the gate, where the inspection reads the tail again. A `fixed` row of a gate amendment's own `## Amendment <n>` table (a review-thread fix) is a cite target too, and its commit counts as that amendment's. A land rebase's patch-identical image of a cited commit is already cited, so the gate doesn't list it. `{ "cite": false, "why": "…" }` keeps it held. To extend a WP's Files before its tail needs it (a lane's ask, an amendment brief that names a new path), run `conduct.mjs ratify --run <dir> --wp <id> --paths <a,b> --why "<the ruling>"`. A path another unfinished WP owns is refused (exit 5).
   - `inspect` with part `visual`: the visual read of a UI WP, owed before a WP whose `**Visual rules:**` names design-direction rules can pass its gate (§ Visual reads). Open the frames its lane took at the action's head, judge each rule in the action's `rules` from the pixels, and record `{ "head": "<the action's head>", "frames": ["<absolute path>", …], "rules": { "<n>": "pass" | "fail: <what the frame shows>" } }`, one entry per rule. A malformed record exits 2 and writes nothing. All pass: the gate runs again and finds the read. Any fail: a gate amendment carrying each failed rule, and the next head is read again.
   - `inspect` (any other part): a judgment step at the merge gate. Run the diff argv in `command` (the post-cap tail: commits added after the last review, as `fixed` rows of it or as a gate amendment's fix, which the gate labels `gate-fix`), read it against the findings the action names, and record `{ "verdict": "addresses-findings" | "unrelated-change", "tail": "<the action's tail>", "head": "<the action's head>" }`. `unrelated-change` holds the PR. A **trivial** tail gets no `inspect` step: the gate passes it and labels it `(trivial)`. A tail is trivial when it has no net diff, or when every path it changes is Markdown that is not a test or fixture and matches no `contractPaths` or `trivialExclude` glob (§ Repo config; without `trivialExclude`, `skills/**/SKILL.md`, `reference/templates/**`, `agents/**`, `commands/**` and `.claude-plugin/**` are never trivial).
   - `touch`: stop and tell the operator what the instruction says. In session, pose it as a plain AskUserQuestion with the recommendation first (the recommended option listed first, its label ending "(Recommended)"), the ask key in each option label (`a — Approve as proposed`), and at most four options per question; split or collapse a touch with five or six. The run reads the answer only through the touch's own channel, below. A chat answer is not a go for a touch: when it and the channel's answer differ, the channel's answer wins, and you tell the operator which one the run took.
     - **Core path:** the operator runs the touch's `answer` command from their own terminal; record `{}` after they have. An unanswered touch returns the same action with `answered: false`.
     - **Session ask (spine path, `part: 'ask'`):** a touch is asked in session first. With the operator in this session, pose it as above and record `{ "key": "<letter>", "text": "<their typed text, or null>" }` from their choice: the answer is `operator:session`, its record is `touches/<n>.json`, and `/spec --preapproved` names that record. Nothing is filed on the Spine. Record only what the operator chose, never an answer you inferred; typed text with no key is option (c), when the touch has one. With no operator in the session (a headless run, a scheduled resume, a successor no operator has spoken to), record `{ "unattended": true }`. A runner that knows it is headless sets `WORKIT_UNATTENDED=1`, and touches skip the ask.
     - **Unattended (spine path):** the touch is filed once, as a plain `needs_input` receipt on the anchor. Its question is the touch's DO/EXPECT text, with the options as text lines when the EXPECT doesn't letter them, and its `stoppedAt` names the resume command. It carries no structured options and nothing is posted anywhere. The next action is a hand-back (`handBack: true`): end your turn and tell the operator the touch waits on them. Never record a hand-back (`record` returns it unchanged with `answered: false`), and never wait or poll for an answer. One touch is filed at a time. The build keeps working while a touch is filed and hands back only when nothing else can act.
     - **The answer comes later.** The operator answers in any later session, which runs `conduct.mjs next --resume <run dir>`: the hand-back is consumed and the touch is asked there (record their choice as above; `{ "unattended": true }` hands back again and files nothing twice). Or they run the touch's `answer` command (in `touches/<n>.md`) from their own terminal, then the resume. Either way the next action is a `supersede` receipt: an ordinary `paused` receipt on the anchor (`completed` when the answer ended the run) whose `did` quotes the answer, so the needs_input stops blocking the board. An answer the run can't use (a budget (a) with no amount) is asked again in session, or re-filed with the reason when it came from the terminal.
   - `wait`: wait `waitMs`, record `{}`, then run `next`.
   - `done`: the run is over. A `done` action is never recorded.
3. **Record it.** `conduct.mjs record --run <dir> --action <id> --result '<json>'` (or `--result-file <path>`). Write a result file and record it in two steps, never in one parallel batch: a refused Write leaves the previous action's file for `record` to read. A tool result of `{}` or `null` and an inspection that names another tail or head are refused (exit 2) and the action stays pending. It prints `{ ok, phase, action }`, the next action: loop to step 2. Re-recording the last recorded id is a no-op; any other id that isn't the pending one is exit 5. `--manual` marks a step you did by hand, so the analysis counts it as crossed by hand rather than owned by the skill. Exit 2 is an invalid result; fix it and record again. **A failure whose JSON output carries a `recorded` field** (the action id; exit 1, or the failing step's own code) means the record landed durably and a later step failed: don't record again with a different result. Run `next` (or re-send the same record, a no-op replay) to get the next action.
4. **Resume.** `conduct.mjs next --run <dir>` (or `next --resume <dir>`) returns the pending action again, with one exception: a pending hand-back is consumed and the touch is asked again (or, answered from the terminal meanwhile, its `supersede` receipt comes first). `conduct.mjs status --run <dir>` prints a summary.

**Let `drive` do the mechanical steps.** After intake, after a resume, and after each action you record, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/conduct-run.mjs" drive --run <dir>` in the background (Claude Code: `run_in_background`) and act only on what it stops at. It runs each `shell` argv, sleeps each `wait` and fills each template `author` (the lane contract, a lane brief, a release bump), recording every result through `record`. It stops at the first action that is yours (`agent-tool`, `skill`, `touch`, `inspect`, any other `author`, a hand-back, a `wake` wait, `done`, or a shell whose program resolves through PATH and PATHEXT to a Windows `.cmd` or `.bat` shim such as `npm`, `reason: "windows-shim"`) and prints `{ ok, stopped, action, performed }`, exit 0: perform that action as step 2 says, record it, and drive again. While a drive runs, `drive.lock` names its pid, host, start and current action, and the driver renews its lease (`renewedAt`) every 20 s; a driver on another host never counts as gone (its clock may be skewed), so if it is, clear its lock with `drive --run <dir> --break-lock --why "<reason>"`. Meanwhile `record`, `next`, `rotate`, `reset-wp`, `replan`, `ratify` and `upgrade-root` refuse with exit 5: wait for it to stop. A nonzero exit is a stop too, with nothing recorded unless it says so: `record-failed` (the action is still pending; `record.error` says why; the shell's result stays in `drive-result.json` and a rerun records it again rather than running it), `after-record` (step 3's `recorded` rule), `reconcile` (a shell started and saved no result: check what it did, then run or record it by hand; with `reason: "timeout"` the shell outlived its timeout, and drive made one best-effort tree kill only if its root was still running, reported as `killAttempted` and `rootExited`, with no claim that the tree is gone: check what it left running before you resume; the next drive stops at `reconcile` too), `spawn-failed` (the program never started; `spawnError` and `message` are the spawn's own), `pending-moved` (the run moved under the drive), or a refusal (an open rotation, or another drive holding `drive.lock`). `drive` and `record` act only on the run their `state.json` belongs to: a copied run dir still names the original in `runDir` and in its pending argv, so either verb pointed at the copy exits 2 ("this state belongs to …") and nothing runs or is written. `--max-steps <n>` caps one drive (default 200). A T3 conductor drives with `--as-thread <its own thread id>`: the thread fence of § Where lanes run is checked before `drive.lock` is taken (exit 5, nothing run), and the id rides every `next` and `record` the drive makes; after a resume, `drive --resume <dir> --as-thread <id>` adopts as `next --resume` does. Each step's start time, id, kind, exit code and duration go to `<run>/drive.log`.

**Exit 4** means this installed version lacks a phase handler or module the run needs (the verb names the path, e.g. `lib/analyze.mjs`): the later phases ship in a later version. Stop and report the path; don't write state by hand to get past it. A stopped WP is put back with `reset-wp` (§ Recovering a stopped WP), never by editing `state.json`.

**A new plugin root.** After a self-hosted release (§ Self-hosted runs) a verb can exit 2 naming a new plugin root. Re-run it with that root's `skills/conduct/scripts/conduct.mjs`, and re-read that root's SKILL.md before the analyze and showcase steps: the text you loaded is the old version.

**Where a run lives.** The workshop is `<runs-root>/<slug>/` with `--runs-root`; else `<workspace>/data/outputs/workshops/<slug>/` under `WORKIT_WORKSPACE_ROOT` or the nearest ancestor of `--repo` holding both `projects/` and `data/`; else `~/.workit/runs/<slug>/`. The run dir is `<workshop>/run/`: `state.json`, `events.jsonl`, `touches/`, `rulings/`, the run's lane contract `_lane-contract.md`, per-WP lane briefs and reports (`lane-<wp>.md`, `lane-<wp>-report.md`), `reviews/`, `council/` and, at the end, `run-analysis.md`. `/spec` writes its workshop files beside it. Lane worktrees sit beside the repo, never in the run dir. After a WP merges, its lane is cleaned up: a herdr lane is swept (pane closed, worktree removed), and an exec or T3 lane's worktree is removed without `--force` (a T3 lane's thread is archived first, since T3 holds the folder open until then; the archived thread keeps the lane's history). Then, if the directory is gone and no other worktree has the branch checked out, the branch is deleted locally and on origin, each only while it still names the merged head. Nothing is forced. Whatever stays is named on the WP's line in the run analysis. The release gets the same cleanup after its `verify` commands: `<repo>-wt-<slug>-release` and `conduct/<slug>/release` go, and what stays is named on the release line. A release that fails before then keeps its worktree for diagnosis.

## Adapters

The **core** runs with `git`, `gh` and one lane-agent CLI. An adapter replaces a core mechanism with a richer one when present.

- **Declared by you.** A script can't see your MCP tools, so declare an adapter only when **every** tool it needs is callable in your own tool list; a partial set means the adapter isn't declared. Intake records each declaration with its evidence (`declared`).
  - `spine`: `spine_quest`, `spine_update`, `spine_receipt`, `spine_author`.
  - `council`: `council_review`, `council_synthesize`, `council_challenge`. A council round leaves no thread on the PR, so at adjudication the build posts one COMMENT review to the PR: every finding's id, the lane's verdict, commit and Evidence cell (`<review dir>/pr-record.md`). A failed post is named under the analysis audit. For a delta escalation, the gate also waits for the posted, head-bound council record. Without this adapter a delta never escalates: its findings are amended at T1 like any others, its review entry says why (`escalation`), and no council round is owed. The audit's judgment lines quote each item's Evidence and link its PR. The council call names `profile: 'conduct-code'`, which is the shared `code` roster minus sonnet-5-carto and is config-owned in the council's `models.json`. A server without that profile refuses the call by name. From round 2 on, the previous round's adjudication (`<review dir>/adjudication-for-next-round.md`) is the first artifact. It tells the council not to re-raise a finding the lane already ruled on, unless the round's change touches the cited code. This is a prompt instruction, not a filter. A conductor or operator ruling on a guard row carries its reason (`Ruling: …`) beside the lane's Evidence.
  - `kb`: `kb_search`, `kb_save`.
  - `verify`: the workit `verify` skill, when it covers the repo's surface.
  - `ledger`: `ledger_write` (the context ledger; a stall alarm's note).
- **Probed.** `intake` asks herdr (`herdr agent list`) only under `--backend herdr`, and refuses when it doesn't answer; otherwise the herdr adapter is recorded off (`chosen`). The probe also covers `notify` and the agent CLIs (a T3 run needs neither CLI). `notify` is an optional shell string in `WORKIT_NOTIFY_CMD`; it is on when set and its program resolves, and off otherwise (on Windows a string holding a double quote is refused). `WORKIT_NOTIFY_CMD` runs after a merge and receives the PR number, the merge sha and a revert command in `WORKIT_NOTIFY_PR`, `WORKIT_NOTIFY_SHA` and `WORKIT_NOTIFY_REVERT`. It also runs for a stall alarm, with `WORKIT_NOTIFY_KIND=stalled` and the alarm in `WORKIT_NOTIFY_TEXT`. A stall is one shell step of a WP failing three times in a row, or a live WP whose state and stage have not moved for 30 minutes. Review actions allow 75 minutes; a queued seat starting or a lens finishing advances progress, while a heartbeat alone does not. A lane at work is left to its deadline. A stall raises an alarm and writes a `stalled` event while the build continues; with the `ledger` adapter declared, a `ledger_write` note goes to the Dogan's ledger stream under `WORKIT_LEDGER_USER` (default `conduct`). An alarm that can't be delivered is recorded as an `alarm-failed` event and never stops the build.
- **Spend is unmetered.** The budget is enforced against the lanes' own logged cost (exec claude lanes' `total_cost_usd`), a lower bound: codex, herdr and T3 lanes log none. Spend books when a lane closes, so the budget gate adds every live lane, and on a dispatch the next WP, at the per-WP projection (the mean of closed lanes, else `laneEstimateUsd`, § Repo config), and each merge records the projected total for the run (a `spend-projection` event and a line on the WP's receipt).
- **`--no-adapter <name>`** forces the core path for one adapter; the names are `herdr`, `notify`, `spine`, `council`, `kb`, `verify` and `ledger`. For a run on the core path alone, declare none and pass `--no-adapter herdr --no-adapter notify`. `claude` and `codex` are agents, not adapters; `--no-adapter claude` is a usage error.
- **kb is declared-only.** There is no probe for kb, so pass `--adapter kb` to turn it on; leaving it to detection leaves it off.
- **kb has no script path.** With kb declared, run `kb_search` on the goal at intake and, once the showcase is answered, `kb_save` of the run's decision record (what the run decided and why, the alternatives it rejected, and the run dir), as your own steps.
- **spine needs `--anchor`.** Choose or author the goal's quest first, then run intake with its id.

## Where lanes run

You choose at intake; nothing is probed into it. **T3 is the default**: running in T3 Code, pass `--backend t3 --t3-project <id>`, the id `t3_project_list` gives for the project whose `workspaceRoot` is `--repo` (compare case-insensitively; register the repo with `t3_project_create` when none is). `herdr` needs `--backend-why` naming what T3 can't do; `exec` is headless, with nothing to watch.

A **T3 lane** is a T3 Code thread bound to the lane's git worktree, so the operator can watch, steer or interrupt it in T3. Conduct cuts the worktree with `git worktree add` (as for exec, `laneSetup` included), then emits `agent-tool` actions you perform and record raw:
- heartbeat: before the first launch, `schedule_task` called from your own thread. It is a 10-minute interval bound to that thread, and its result's `boundThreadId` is the conductor thread the run stores (`state.t3Wake`). It starts a turn in your thread even when the thread is idle, and covers lane deadlines, stalls and a lane that ends without its done message. `analyze` deletes it. A delete that fails stays owed: it is retried at each later wait and at `analyze`, up to 3 attempts per task, and the run analysis's audit names one still left, with the `delete_scheduled_task` call to make.
- start: `t3_thread_launch` with `existing_worktree`, the lane's model (`claudeAgent` or `codex`, effort high) and the brief as its message. It has no idempotency key: if its response is lost, find the thread by title with `t3_thread_list` and record that, never launch twice. With the heartbeat live, the message ends with the lane's last act: a `t3_thread_send` (`mode: queue`, a `…-done` request id per round) into your thread, saying the lane is done and where its report is.
- amendment: `t3_thread_send` (`mode: queue`) into the same thread, so the lane keeps its context. It carries the done send too.
- wait: with the heartbeat live, when every WP waits and the soonest wait is a T3 lane's, the build's yield has `wake: true` and says **end your turn**. It is the one `wait` you don't sleep through. A lane's done message or the heartbeat starts your next turn: record `{}` for that yield, and the build reads every live lane once (`t3_thread_read`, activity view, limit 1, runLimit 1). A wake is news, not a verdict, so the read decides: a run still going waits again, an ended one is reaped and checked, and a failed or interrupted one blocks the WP. Without a live heartbeat, `t3_thread_wait` (2 min) polls, and each timeout is followed by the same read.
- stop: `t3_thread_interrupt`, then a `t3_thread_wait` confirming the run ended.

A tool call that fails is recorded as its error (`{ "error": "…" }`) and blocks the WP with it. A heartbeat's failure never blocks: a `schedule_task` that fails or binds no thread leaves the run's lanes polling.

T3 shows a lane waiting on a person (an approval, a question) as an ordinary running turn, and counts the request in the thread's `pendingRequestCount`. Every read checks that count, so a lane blocked on a person blocks its WP as `dialog` at once. A second read of the latest activity names the approval or question. Don't answer it yourself; it goes to the operator in the blocked touch. Give lanes a full-access runtime all the same: under `approval-required` a lane stops at its first tool call. Its done send also needs your thread's modes to be no broader than the lane's.

A heartbeat belongs to the conductor that made it. After a rotation the lanes poll until their next wait deletes the old heartbeat and makes one bound to the successor. When the pending action is a wake yield, custody does it first: a `schedule_task` from the successor's thread, then the old heartbeat's delete, then one tick that reads every live T3 lane before the run yields on wakes again. A lane launched before the rotation still sends its done message to the old thread, so the successor sees it at the next heartbeat. A predecessor woken by that message ends its turn.

A T3 conductor passes `--as-thread <its own T3 thread id>` on every `next` and `record`. The id is `orchestrator_capabilities`' `parentThreadId`, or `t3_thread_configuration`'s `threadId`; both equal the `boundThreadId` the heartbeat stored. While a live heartbeat is bound to the run's conductor thread and you name another, the verb exits 5 with `not this run's conductor (current: <id>)` and changes nothing: end your turn. A retired conductor's thread is always refused: completed custody adds the outgoing one to `retiredConductorThreads`, and an adoption adds the one it replaced. A successor binds custody to its own thread with `next --custody <n> --as-thread <id>`, and until custody is taken every other thread is refused, the outgoing conductor's included. With no live heartbeat (deleted at `analyze`, or failed), a fresh session's `next --resume --as-thread <id>` adopts its thread as the conductor thread (event `conductor-adopted`) and retires the thread it replaced. With T3 lanes live it queues a fresh heartbeat from that thread, replacing any an earlier adopter left queued or pending; a heartbeat result bound to any other thread is refused, its schedule queued for deletion (event `heartbeat-misbound`). Without `--as-thread` (herdr, exec, by hand) nothing is checked.

## Touches

Every touch step's action and event, `resumed` included, carries the seam `operator-touch`. The one exception is the release anomaly's touch, the blocked touch opened when the release PR's merge is flagged (`land merged --wp release` exits 5). While the release waits on that touch, every touch action it emits carries `release`, and so do their events. That covers the anomaly touch's ask, receipt and hand-back. It also covers the ask and hand-back of a touch still filed ahead of it, which the release emits first. The run analysis reports touches in their own `Touches` section, not as a seam row, and `operator-touch` isn't a send-back seam name.

1. **Touch 1, before `/spec`.** Options: (a) approve as proposed, (b) approve but hold at PR boundaries, (c) approve with changes (free text), (d) decline. The question leads with a short briefing (the repo, what the run will do and whether it merges, the budget, where the lanes can be watched), then the goal and the DO line, and only then the probe details. The answer is the run's only source of merge, release and budget authority. After a (c) answer, an `author` action has you write `touches/1-grant.json` from the operator's text, each field no wider than (a); if the text doesn't settle a field, write `{ "ambiguous": true, "why": "…" }` and the run asks again. A repo with no CI workflows that can gate a PR is offered hold-at-PR only. The budget is **unmetered** and is enforced against the lanes' own cost, a lower bound.
2. **Touch 2, the showcase.** After `analyze`, an `author` action (`showcase-brief`) has you write `run/showcase-brief.json`: `delivered`, `proof` (the runtime evidence, quoted), `notDone` (in plain words; it must name every WP that didn't finish, or state their count above six), `check` (the one thing worth checking yourself), `recommend` (`a`, `b` or `c`) and `why`. Each text field is at most 180 characters. The operator answers from this briefing alone, in session or from its needs_input, so it carries your judgment: never leave a recommendation only in chat. The question leads with it, the recommended option's label says so, and the status lists follow. (a) accept, (b) accept with notes, (c) send back: write `seam: <name>` in the text (an unknown name records no seam). A (c) ends this run as `sent-back`; nothing re-runs and merged work isn't touched again. Reopening is a new `/conduct` run whose goal cites the old run dir.
3. **Touch-1 (b) holds, it doesn't deadlock.** A WP that passes its gate without merge authority ends `held` (PR open, merge lock released); its dependents are `deferred`; the run still reaches the showcase. Merge authority covers a two-way door only: a WP whose PR body's `## Merge danger` says `Door: one-way`, or declares no valid door, ends `held` the same way with authority granted.
4. **Blocked stop.** A WP goes `blocked` with a cause (`error`, `dialog`, `needs-conductor`, `deadline`, `admission` or `cleanup-unresolved`) when a lane asks something evidence can't settle, its deadline passes, a repo-scope fork appears, or the budget cap is reached. It is counted as a touch. Other WPs not depending on it keep going, and the build doesn't end while a blocked touch a WP owns is open. An attributed answer resumes that WP at its `check` step.
5. **A lane's question is ruled by you first.** From the lane's `## Needs conductor` ask, settle it from evidence and write `rulings/<wp>-<n>.json` as `{ "ruled": "<key>", "evidence": "…" }`; write `{ "escalate": true, "why": "…" }` only when no evidence can settle it. Only an escalation opens the operator's blocked touch. A report that says `built` and still carries asks gets the same ruling before review, and each ask is ruled once. A report still `stopped: needs conductor` when every ask in it is already ruled is a failed check: the lane is re-prompted once to act on its rulings, then the WP blocks. When the ruling needs paths outside the WP's Files, add `"ratify": ["<path>", …]`: they are added to its Files with the ruling, and a path another unfinished WP owns is refused. A ruling is recorded as a `ruled` event and a `rulings[]` row, and goes to the lane as an amendment. That amendment doesn't move the delta review's start: the delta review still covers every fix made since the review's findings, Markdown-only ruling or not.
6. **Never advance without the operator's own answer to that touch.** An answer is their AskUserQuestion choice in a session they are in, or their terminal `answer`; nothing else confers authority. A filed touch's question begins `[conduct <slug> touch <n>] (run <runId>/<filing>)`. A quest leaving WAITING, a summary in chat or a later receipt by anyone is never an answer.
7. **The `answer` command is the operator's, never yours.** A core touch, and a spine touch once filed, is `touches/<n>.md` plus the exact `conduct.mjs answer --run <dir> --touch <n> --key <a..f> [--text "…"]` command, which the operator runs from their own terminal. It refuses a non-TTY stdin, so your Bash tool can't run it. Don't try to work around that refusal.
8. **The approval boundary.** The TTY guard and the `by` attribution are a procedural boundary, not proof of the operator's identity (§ Authority).
9. **The budget touch.** When spend reaches the budget, a blocked touch opens that no WP owns. (a) needs the text `budget <USD>` above the spend at the halt (`$` and thousands commas allowed): it becomes the budget. (b) stops new paid lane work (no dispatch, lane start, prompt or fallback); PRs already up are still reviewed and still land.
10. **The `liveness` touch is a blocked-touch cause too.** When an exec lane's exit can't be verified past its deadline (three reads), its WP keeps the lane slot and Files and a `liveness` touch opens: (a) you confirm the process is gone, so the slot and Files are released and the WP keeps its state; (b) they stay held.
11. **No CI at head is never an amendment.** A repo with no workflow that can gate a PR stops at once; otherwise the gate waits 30 minutes per head for CI to appear, then stops. The stop is `held` (`held at PR: <reason>`) without merge authority, and `blocked` with it.
12. **The recover touch.** When nothing else can run and a WP blocked at its gate (not in a lane check or a review), with its PR open and not squashed, no adjudication owed and its lane verified, the build doesn't end. A `recover` touch opens for that WP, naming its block reason and the WPs deferred on it. (a) conduct runs `reset-wp --to land` for it on the operator's word, and what waits on it returns to `pending`. (b) it stays blocked and the build ends; the showcase names it not done. A WP blocked because the operator stopped paid lane work at the budget touch gets no recover touch. A filed showcase stops every reset, so this touch is the run's last chance to reach its goal.
13. **A gate command that failed only on timeouts is retried, not amended.** The build reads the failure listing that node:test's spec reporter or vitest's default reporter prints. When every listed failure is a timeout, or a child that its parent's timeout cancelled, the host ran the suite too slowly. The merge lock is released and a `quiet` probe runs in the background (`conduct.mjs quiet`: busy CPU across every core under 30% in three one-minute samples). A busy host waits 5 minutes and is probed again, up to 6 probes, and then the WP lands again from its rebase. The probe reads the whole host, so the run's own lanes count as load. Each head gets 2 such retries and each WP 4, and the next all-timeout failure is a gate amendment. A failure of any other kind, output the build can't read in full, or output holding both runners' listings is an amendment as before.
14. **Expected checks, and a reused pass.** When branch protection is unreadable, the gate expects the checks that the base commit's runs made from a trigger a PR head also gets (`push`, `pull_request`). A check only a `schedule`, `workflow_dispatch` or `pull_request_target` run made is not expected; a check no workflow run accounts for still is, and so is a `push` workflow filtered to the default branch (the run doesn't show its branch filter: declare `ci-checks` for it). A gate command's pass is recorded with its head and the argv and env it ran, when the suite ends with the worktree at that head and nothing uncommitted. A land reset that comes back to that head with the same command (after a `ci-checks` policy, say) skips the suite and goes straight to the land gate. A new head, a changed command or a changed `gateEnv` runs the suite again.
15. **A gate amendment answers its review threads.** When the land gate stops on unresolved review threads, it lists them by first comment id, and the gate amendment's brief names those ids. The lane answers each thread it settles in its `## Amendment` table, keyed by that id. When the amendment's check passes, conduct replies to each answered thread and resolves it, the same way it does after a review round's adjudication (`fixed`, `refuted` and `judgment` rows alike), before the next gate reads the threads. A thread with no row, a row for an id the gate didn't list, and a `conductor` row stay open, so the gate stops on them again. Only the listed threads' rows are read and validated; a table that answers one of them twice is a failed check, and the lane is asked again with the reason. A reply that fails to post blocks the WP and names the failure, and no thread is resolved. A posted reply is recorded with its comment id and its answer (verdict, evidence, commit): a later amendment that gives the same answer resolves the thread without replying again, and a changed answer is posted. The rows don't change the review's verdicts.
16. **A claude lane checks itself before it stops.** Every claude lane, exec, herdr or T3, carries a command Stop hook (a T3 lane's rides its worktree's `.claude/settings.local.json`, written by `lane hook` and kept out of commits by the repo's `info/exclude`) (`scripts/stop-check.mjs`, `conduct.mjs lane stop-check`). Each time the agent tries to end its turn, the hook runs this backend's report, PR-lookup and PR checks, read-only. A failure you would amend blocks the stop, and the agent gets your reason as its next instruction, at most 3 times per session and amendment round. Refuted, needs-conductor and infrastructure failures let it stop. A stop with a background task running is never blocked, and a herdr wait holds on it for up to 15 minutes. Each stop's verdict (`pass`, `blocked`, `failed`, `released`, `background-live`) goes to `lane-<wp>-stopcheck.json` in the run dir, and `lane.stopCheck` carries the latest one. Your own checks still run after the lane stops; the verdict never replaces them. Codex lanes carry no hook: Codex skips a hook from an untrusted path without a word, and every lane worktree is a new path.

## Authority

Merge, release and budget authority is what touch 1's answer recorded in `state.authority` (a (c) answer's checked grant included), with the budget raised by a budget touch's (a). Nothing is signed: the authority lives in `state.json`, and conduct trusts it. An agent that edits `state.json`, or a stored action in it, can widen what the run does; conduct emits each pending action and queue head as stored. The run analysis and the handoff print the authority as recorded.

## Runtime verification is part of done

> **Runtime verification is part of done.** A change that alters runtime behavior is exercised at runtime before the PR boundary, and the report quotes the command and what was observed. A runtime check must be able to fail: say what it would have shown if the change were broken, or run it once against the pre-change tree — otherwise it is vacuous and is reported as such. Where the claim is visual, one screenshot per claim, of the critical state only; evidence is a few decisive pictures, never a gallery. Code-only verification of a runtime change is reported as **not exercised at runtime**, never as done.

Every lane brief carries this rule. Each WP's `**Runtime exercise:**` field names the surface (a CLI run against a real input, a service probed, a page loaded, or `none: <why>`) and the check; an empty field means the lane names the surface itself, and it doesn't authorize `no runtime surface`: only a field that begins `none` (case-insensitive) does, and the expected form is `none: <why>`. A waiver with no reason passes the gate but is reported as one. The lane writes the evidence under `## Runtime exercise` in its report, with a `Verdict:` line and, for `exercised`, a `Would have shown:` line. A missing section, `not exercised` for a WP that names a surface, or a `vacuous` check (unless the WP says `none`) fails the lane's check, and the lane gets an amendment before review. The workit `verify` skill is an optional adapter: when it covers the repo's surface, a WP's runtime exercise may name it, and its verdict artifact is the evidence.

## Visual reads

A goal with a UI gets its pixels judged at the merge gate, not only its code (quest 1b3dec9f). `/spec` writes the rules (§ Stage 4 there); this skill enforces them:
- **The rules.** The orchestrator's `## Design direction` (a lite spec's `spec.md`) holds numbered rules at column 0, each with its indented continuation lines; among them, rules opening `**Palette:**`, `**Type scale:**`, `**Iconography:**` and `**Fit to view:**`. A section missing one, or with a number used twice, is a spec defect at mint.
- **Which WPs.** A WP's `**Visual rules:**` names rule numbers, `all`, or `none`. Its lane brief carries them, and the lane names its frames under `## Runtime exercise`.
- **The polish WP.** With a design direction, the orchestrator's last wave is one WP whose `**Skills:**` names `frontend-design:frontend-design` and whose `**Visual rules:**` covers every rule. The lane brief names every skill a WP's `**Skills:**` lists.
- **The read.** After the gate passes at a head, a WP with visual rules gets the `inspect` `visual` action; the merge waits on it. The record's `head` is your attestation that the frames show that head: the verb checks that the files exist, not where they came from. Each read is kept on the WP, and the run analysis lists them under `## Visual reads`.

## Self-recovery before a blocked stop

Try these first. A blocked touch is for what they can't settle.

- **A failed review seat:** re-run it once; then use a seat outside the author's model family, never one the operator excluded.
- **Red CI:** name the oracle that failed, and rerun a flake. CI still running is a `wait`, never a failure.
- **A stuck lane:** read its pane or log, re-arm the wait, then amend. A lane keeps its slot and its files until its process is observed exited, so don't start another WP on its files while it runs. The lane cap counts lane agents: a landing WP (at `gate`, or waiting on the merge lock to start its land) whose lane has exited keeps its Files but frees its slot, since you land it with no agent. It doesn't count toward the 3rd-lane memory check either. A gate amendment starts the lane again, so it waits for a slot (a `wait` naming the WPs that hold them), and while it waits no new WP is dispatched ahead of it. An amendment to a herdr lane whose agent has exited starts the lane before prompting it; a live lane keeps its agent.
- **A harness dialog** (a `block` with cause `dialog`): the verb re-polls once after about a minute, then blocks. **Never answer a harness dialog yourself**: not by sending keys, not by approving. It goes to the operator in the blocked touch.
- **A council split:** you break the tie, inside the goal's bindings, and record why.
- **A fix loop that repeats a class:** when review round N's findings share a defect class with round N−1's (the same bypass, reached by another path), another fix lane buys the next instance, not convergence. The round-N findings brief carries your design ruling instead: the one mechanism that removes the class, or the WP's claim narrowed to what its fixes prove, with the rest named as residuals. Rule each finding against it in the brief. A ruling wider than the approved scope is a re-plan (§ Re-planning mid-flight); one you can't settle from evidence is a blocked touch.
- **A refuted premise:** a lane whose report says `refuted` ends its WP `refuted` and defers its dependents; that is a finding, not a failure to retry.

## Recovering a stopped WP

When a WP is `blocked` or `held` for a cause you have since fixed outside the lane (your brief's wrong path or table header, a PR body, the repo config), put it back with the verb. Never edit `state.json` by hand.

```
conduct.mjs reset-wp --run <dir> --wp <id> --to <target> --why "<what you fixed>"
```

| `--to` | From | The WP becomes | Use it when |
|---|---|---|---|
| `check` | blocked; or amending on a failed check's re-prompt whose brief is still pending | `amending` (or `dispatched` before any amendment) at `check` | the report or PR is fixed; re-run the lane's checks. From amending, the pending brief is dropped and the re-prompt withdrawn, so your own fix costs no lane round |
| `checked` | blocked, with a PR recorded | the same, at `checked` | the report is right as written; rule its asks and adjudicate its table |
| `prompt` | blocked | the same, at `wait`, its brief queued | the brief is fixed; a herdr lane whose agent exited is started first, an exec lane resumes its session |
| `wait` | blocked, herdr lane | the same, at `wait`, the lane's deadline renewed | you restarted the herdr lane agent and sent its brief yourself |
| `land` | blocked or held, PR not merged | `gate` at `land` | the PR is ready; rebase, gate and merge again. A land takes no lane slot, so it's admitted with every slot taken |
| `setup` | blocked, exec lane, its agent never started | `dispatched`, the repo's `laneSetup` queued in the existing worktree, then brief and start | you fixed what made `laneSetup` fail (a lockfile, a registry, the command) |
| `pending` | dropped (by a re-plan), or blocked before its lane worktree existed (an unusable `laneSetup`) | `pending`, no lane | the plan wants it again; the scheduler dispatches it under its usual rules |
| `delta` | blocked or held, PR not merged | `pr` at `delta` | review an uncovered tail; requires `--baseline <sha>` verified against the latest full review |

For `delta`, use `--to delta --baseline <sha>`. On the original commit line the baseline must be the reviewed head. After a recorded rebase, the supplied commit must carry exactly the reviewed prefix from the recorded new base. Verification reuses the review-round mapper's patch identity and location checks: changed parent files, ambiguous hunks, missing history or a baseline that includes unreviewed fixes are refused. The worktree must be clean and its HEAD must match the recorded PR head. Unsettled findings and a latest review already marked `delta` are refused too; a reset does not grant another review past the cap.

A successful delta reset records its verified baseline, clears the stale gate result and this WP's merge lock, and reviews the tail even when it contains only Markdown. The mapping is bound to that reviewed head and candidate; a candidate that moves needs a new verification. New findings start an exited herdr lane before its amendment prompt.

Under the run's lock the verb copies `state.json` to `state.before-reset-<wp>-<time>.json` beside it, sets the WP's reason to `reset-wp --to <target>: <why>`, and replaces its queue: `check`, `checked`, `land` and `delta` keep a queued stop, so an agent still running is stopped first. It returns every WP deferred because of this one (directly or through another deferral) to `pending` and logs a `wp-reset` event on the `recovery` seam, which the run analysis counts as crossed by hand. When the build had ended (phase `release`, `analyze` or `showcase`, with no release run and no showcase touch filed), the run goes back to `build`: the pending action of the phase it leaves is dropped and the release is decided again when the build ends. The check and gate counters are kept, so a WP that has used its one check re-prompt blocks on the next failure. Then run `next`.

Every target except `pending` puts the WP back in a live state, so the scheduler's rules still hold (`pending` takes no lane, and the scheduler admits the WP later): a WP whose Files overlap a live WP's (a landing WP included), or any reset but `--to land` while every lane of the run's cap is in use, is refused until a lane finishes, and so is any reset while a merged-tree halt is open. It also refuses (exit 5) any other state or target, a WP with an open touch (answer it instead), an unverified lane (answer its liveness touch), a WP whose action is pending (record it first; only `--to check` drops a pending re-prompt brief), and a run past its release or showcase. Exit 2 is an unknown WP or target, a missing `--why`, or a run another verb holds locked. A refusal writes nothing, no snapshot included.

## Re-planning mid-flight

When information that arrives mid-build shows the plan is wrong, or that another course is clearly better (a WP's premise refuted by a merged one, a cheaper route a lane found, a lane that consumes a route or schema no WP owns), restate the plan as a delta and record it before acting on it (quest e830d835):

```
conduct.mjs replan --run <dir> --plan <file>
# file: { "why": "<the new information>",
#         "delta": [ { "change": "<what changes>", "door": "two-way" | "one-way", "inScope": true | false } ] }
```

- **Every change two-way and inside the approved scope:** the re-plan rests on the run's pre-approval and needs no operator. The verb writes the proposal to `rulings/replan-<n>.json`.
- **Anything wider** (a one-way door, or a change outside the scope): dispatch halts on a touch whose question carries the whole delta-plan. A plan too long for one question is refused (exit 2). (a) approves it, (b) keeps the original plan, (c) approves it as the operator's text amends it, so (c) needs the text. Live lanes finish, and the build waits on the answer rather than ending. Any usable answer clears the halt.
- **Re-plan at a wait, or with the record that shows it.** The verb refuses while any other kind of action is pending (exit 5), because an emitted action would run before the re-plan. When an action's own result is the new information (WP-02's final result makes WP-03 unnecessary), file the plan with that action's record: `conduct.mjs record --run <dir> --action <id> --result <json> --replan <file>`. The re-plan is filed after the record and before anything is emitted, so its apply step comes before the dispatch that record would have started. Before anything is recorded, the verb refuses a malformed plan (exit 2), a run outside `build`, an open rotation, and a touch's step (exit 5). A refusal that depends on what the record changed comes after it (exit 5, or 1 for an unexpected error). The output then carries `recorded: <id>`, which is authoritative: the record stands, nothing is emitted and no action is pending, so fix the plan and run `replan`, then `next`. A replay of that record with `--replan` files nothing. It returns the re-plan the record filed, and it is refused if the record filed none.
- **An approved re-plan is applied first.** The build's next action is an `author` step: make each change with the verb that makes it (`ratify`, `reset-wp`, a ruling's amendment), then write `{ "applied": true, "what": "…" }` (or `{ "applied": false, "why": "…" }`) to its `outPath`. A pending WP the plan no longer needs is dropped there with `"drop": ["WP-03"]`. It becomes `dropped`, with the re-plan as its reason, and its dependents are deferred. The analysis and the showcase name it as not finished. A drop is two-way inside the run: `reset-wp --wp WP-03 --to pending --why "…"` puts it back, and the scheduler dispatches it again. With the Spine adapter, an autonomous re-plan is then receipted on the anchor (`completed`: what changed, why, the pre-approval it rests on, what was applied). The receipt waits while a touch is filed on the anchor.
- Door and scope are your judgment, read the same way as a PR's `## Merge danger`. In doubt, it is `one-way`. Only one re-plan may be open at a time: one waiting on the operator or one approved and not yet applied. The run analysis lists every re-plan under the pre-approval audit.

## Greenfield bootstrap

`conduct.mjs bootstrap --repo <abs> [--write] [--offline]` checks a repo against the greenfield manifest (`${CLAUDE_PLUGIN_ROOT}/reference/templates/repo/manifest.json`). The manifest's standard is a repo prepared as if it will go public: README, LICENSE, SECURITY.md, `AGENTS.md` with a `CLAUDE.md` `@AGENTS.md` stub, `.editorconfig`, `.gitignore`, a CI workflow that runs on PRs, cancels superseded runs, sets `timeout-minutes` and scans with gitleaks, dependabot, and a PR template carrying `## Merge danger`. A repo with `package.json` adds a Node pin, `engines.node`, a formatter config and npm in dependabot. The one repo setting checked is `deleteBranchOnMerge`.

- It prints one JSON report. Exit 0 means every applicable item passes, 3 means something is missing, incomplete or unverified (`failing` lists each), and 2 is a usage error. A setting `gh` cannot read is `unverified`, never a pass. `--offline` skips settings and says so.
- `--write` copies a template (`reference/templates/repo/files/`) for each missing file. It fills `{{name}}`, `{{year}}` and `{{owner}}` (origin's repository name, else the repo directory; the UTC year; and `git config user.name`). It never rewrites a file that exists. A file that lacks a required marker, and `engines.node`, are reported for a hand edit. It writes the working tree only: no commit, no branch, and no change to a repo setting. The report prints the `gh repo edit` fix.
- A private repo's report names `${CLAUDE_PLUGIN_ROOT}/reference/templates/repo/public-flip-checklist.md`. That list covers branch protection, secret scanning, push protection, Dependabot alerts and private vulnerability reporting, which a private free-plan repo cannot turn on, as commands to run on the day it goes public.

**In a run (quest 977d3efb).** `intake` turns the check on when the repo has no CI workflow that can gate a PR (`intent.ciWorkflows` 0) or at most 3 commits on HEAD. An unread workflow count is not a trigger, and neither is a shallow clone's commit count. The trigger and its reasons are stored as `intent.greenfield` and named on touch 1. Mint then binds the manifest to WP-01: WP-00 in a one-WP run, else the first WP by wave. Every applicable manifest item that fails on the checkout adds its path to that WP's Files, and absent paths are added as Create paths. A stack's items apply when the repo has its file or the WP's Files name it. The WP's brief gets a `## Greenfield bootstrap` section telling the lane to run `bootstrap --write --offline` on its worktree and finish the hand edits. Its `land gate` runs `bootstrap --repo <worktree> --offline`. While that exits 3, or while a file the check read is not committed at HEAD, the gate fails with cause `bootstrap`, which is an amendment. Any other non-zero exit is `infra`. The gate checks files only, because a lane can't change a repo setting; the lane runs the read-only online check once and names each `gh repo edit` fix under `## Follow-ups`.
## Rotating the conductor

When your context runs high (the session-chain skill's rotation policy), hand the run to a fresh conductor with the verb. Never write the handoff by hand.

```
conduct.mjs rotate --run <dir> --why "<why now>" [--model <id> --effort <level>] [--name <successor>]
```

Run it right after a `record`, before you perform the action that record printed: the successor performs that action as given. It writes `<run>/handoff-<n>.md` from `state.json` (the phase, the pending action, every WP with its lane, PR and queued step, open touches, the authority and spend) and prints what to do next:
- **Inside herdr** (`HERDR_ENV=1` and `HERDR_PANE_ID` set; `--model` and `--effort` required) it prints a `session.mjs chain` argv with the handoff and `--log <run>/session-chain.jsonl`. Run it as your last tool call. If it exits nonzero and the successor was briefed (`callerRetirement: exit-refused`), end your turn: the successor takes custody. Otherwise run `next` from your own pane: it cancels the rotation and gives you the pending action back.
- **Outside herdr** start a fresh session with `Read <handoff> and execute it exactly.` and end your turn.

The successor's first call is `next --custody <n>` (the handoff gives it); custody never starts without it. It exits 5 when rotation `<n>` was cancelled or superseded: that session is not the run's conductor and ends its turn. Otherwise it emits **custody** before anything else, and until custody is taken `record` accepts only custody steps and every other writing verb (`ratify`, `reset-wp`, `ci-checks`, `lane spawn`, `upgrade-root`) exits 5:
1. Retire the predecessor: `session.mjs retire <its pane> --mode close --expect-session <its session>`; if that exits nonzero, `--mode exit+close`. The session comes from the chain row in `<run>/session-chain.jsonl` for this handoff and pane, so a pane id herdr has reissued to another agent is never retired. If both fail, if no chain row names the session, or if the predecessor ran outside herdr, an `author` step asks for `<run>/custody-<n>.json`: `{ "gone": true, "evidence": "…" }` once you have seen it end, or `{ "cancel": true, "why": "…" }` when you are that predecessor and no successor took over.
2. With the Spine adapter, a `paused` receipt on the anchor naming the rotation, the handoff and how the predecessor was retired. It is skipped while a touch is filed on the anchor, so the operator's needs_input stays the latest receipt. A receipt that fails is logged and never blocks custody.

Then the run emits its pending action again, by the same id (a pending hand-back is consumed and the touch asked again, as on any resume), and the build polls every live lane from its queue: nothing is re-armed by hand. From the predecessor's pane, once the successor has started custody, `next` and `record` exit 5. A second `rotate` while one is open exits 5, and so does `rotate` at the showcase (the analysis is already written; a fresh session resumes with `next --resume`). Each step is an event on the `rotation` seam, so the run analysis shows the row as owned.

## Repo config

Conduct-only keys live in the workspace, keyed by the repo's GitHub identity: `<workspace>/data/config/conduct/<owner>/<repo>.json`. The workspace is `WORKIT_WORKSPACE_ROOT`, else the nearest ancestor of the repo holding both `projects/` and `data/`. `intake` reads that file once and pins it: it stores the parsed keys in `state.json` and puts the file's sha256 on touch 1, which with the Spine adapter is the anchor receipt. The build and the merge gate read only the pin. An edit to the file after intake does not reach the run. An unknown key, a key of the wrong type, a `release` that is not a valid recipe (checked even under `--release`) or a `laneSuite` in this file is exit 2 at intake. With no workspace file and no repo file, touch 1 says `Repo config: none` and names the path it looked for.

The lane-facing text goes in the repo's `AGENTS.md`, under a `## Lane suite` heading (`###` or a setext `---` underline also counts). Its body, up to the next heading or thematic break, is joined into one line (fence markers dropped) and becomes the lane-isolation line of the lane contract and its `## Run deltas` entry. Keep it to a short paragraph. A deep spec can set its own: a `## Lane suite` section in `work-packages/_orchestrator.md` replaces the repo's for that run (an operator rule such as "no database suite on this host"), and the run analysis names it as the source. It changes what lanes run, never the conductor's gate.

The workspace file may carry:
- `release`: the release recipe (`--release` overrides it).
- `contractPaths`: globs that raise a WP to T2. Conduct also raises agent-action
  hook and command-gate paths without a repo config entry; see `burn-down` § Per item step 3.
- `trivialExclude`: globs a tail never counts as trivial.
- `gateEnv`: env for the conductor's gate command. `{run}` and `{wp}` become the run slug and the WP id as lowercase identifiers. Use it for a repo whose suite needs its own database per runner. `{run}` is at most 24 characters and the same in every key: a longer run keeps its first 11 characters and a 12-hex sha256 of the whole normalized run. So a database name of up to 39 fixed ASCII characters plus `{run}` fits Postgres's 63-byte identifier limit, and runs that share a head stay apart. A templated value with no `/` or `\` that still expands past 63 bytes is refused, and the WP blocks at its gate; URLs and paths are not measured.
- `gateBackground: true`: the gate command's action carries `background: true`.
- `laneEstimateUsd`: what the budget gate counts for each live lane and the next WP until a lane has closed (then the mean of closed lanes is used); default 15.
- `laneSetup`: a command string (no double quote) run in each new exec lane worktree, after `git worktree add` and before the agent starts, e.g. `npm ci`. A non-zero exit blocks the WP. Prefer a real install to a junction: conduct removes a merged lane's worktree with `git worktree remove`, and older Git follows a junction inside it. Herdr lanes run none yet.
- `laneDeadlineMinutes`: how long a lane may run from its start or its latest amendment before it's stopped and blocked `deadline`; a whole number from 1 to 720, default 120. Raise it for a repo whose cold builds take most of two hours.

**Deprecated, still read:** `.workit/conduct.json` in the product repo, with the same keys plus `laneSuite`. With no workspace file it supplies the conduct-only keys as it always has: the build reads it from the checkout and the merge gate from `origin/<default>`. With no `## Lane suite` section in `AGENTS.md` it supplies `laneSuite`. Touch 1 and the run analysis's Pre-approval audit name it as a deprecated location. A run started before this split has no pin in `state.json` and reads the repo file the old way, `laneSuite` included.

## Self-hosted runs

When the target repo is the plugin running this skill, lanes never invoke `/conduct`: a lane building the skill tests it with fake executors only. The release phase runs the repo's recipe; after the plugin update, re-read the new SKILL.md and use the new script (§ The loop, "A new plugin root").

## Refusals

`intake` exits 2 and writes nothing when:

1. `--repo` is missing, or isn't a git work tree.
2. The repo has no `origin`, or `gh` can't resolve it as a GitHub remote.
3. `gh auth status` fails.
4. **The goal names more than one repo.** Only you can see this: refuse a multi-repo goal rather than pick one.
5. No lane-agent CLI (`claude` or `codex`) is on PATH (herdr and exec runs only).
6. A run already exists for the same slug (use `--resume`).
7. `--adapter spine` without `--anchor`.
8. With the Spine adapter, touch 1's question would be over `spine_receipt`'s 2,000-char cap. A goal over 300 chars is already cited by its file (`<run>/goal.md`, written at intake), its length and its opening line, so what remains to shorten is the release recipe or the repo path.
9. No `--backend`; `--backend t3` without `--t3-project`; `--backend herdr` without `--backend-why`, or with no herdr server answering.
