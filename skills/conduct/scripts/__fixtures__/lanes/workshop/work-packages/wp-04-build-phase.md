# WP-04: The build phase

**Execution:** review-needed · **Review tier:** T2 (adds tests that claim to prove the build loop's scheduling, landing and recovery) · **Lane model:** Opus 5.5/high · **Line budget (E3):** ~600 production lines

**Precondition:** WP-02 and WP-03 merged to `main`: `lib/schedule.mjs`, `lib/lanes.mjs` (with `recordLaneStep`, `chooseBackend`, `parseOutcome`), `skills/conduct/templates/lane-brief.md`, `lib/land.mjs` (with `recordLandStep`, `parseAmendmentTable`, `resolveThreadActions`, `mergeLockFor`), `lib/release.mjs` and `.workit/conduct.json` exist with the exports named in `_orchestrator.md` § Module ownership. Read `_orchestrator.md` first: § Build scheduling, § Action (steps, seams, consumption), § Touch flow and the WP states are what this phase implements.

**Goal:** write `lib/phases/build.mjs`, the phase that turns the WP list into merged (or held) PRs: the run's lane contract, the scheduler glue, the per-WP lane loop routed through the two recorders, conductor rulings on lane questions before any escalation, review, adjudication and thread resolution, the serialized rebase → gate → merge under the merge lock, blocked recovery, deferral, and the budget check; and prove it with unit tests on a fake executor in `lib/phases/build.test.mjs` (D19.29).

**Files:**
- Create `skills/conduct/scripts/lib/phases/build.mjs`: `next`, `record`, `RUN_SLOTS`, and the emitter.
  - **Lane contract (D15.2):** the first action of the phase, once per run, is an `author` action (step `contract`) from `<pluginRoot>/reference/templates/lane-contract.template.md` to `<run>/_lane-contract.md`, whose `slots` fill the template's run-level slots (run name, anchor or `none`, the run-state path in place of the run doc, repo and gate command, base branch, reports directory, and the per-repo lane isolation line). `RUN_SLOTS` lists the run-level slot prefixes (D17): `<run name>`, `<anchor short id>`, `<absolute path to the run doc>`, `<repo A` (prefix: also matches `<repo A worktrees: …>`), `<gate command(s)>`, `<reports directory>`, `<base branch per repo`, `<Per-repo lane isolation`, and `<repo B` (a single-repo run deletes the `<repo B` lines). Per-lane placeholders (`<id>`, `<lane>`, `<n>`, `<sha>`, `<path>`, `<your-lane-id>`) stay. The gate command is the orchestrator's `## Gate Commands` line for the WP's `wave` (deep; `wps[].wave`, D18) or `state.spec.gateCommand` (none/lite). **Suite ownership (D19.30):** the `<Per-repo lane isolation …>` slot is filled from the target repo's `.workit/conduct.json` `laneSuite` (read through `deps.read`; workit's says lanes run the full `node --test`), else with `none declared`, so template rule 9 stands for repos that declare nothing. **Run deltas (D20):** when `laneSuite` is set, the same `author` action appends a `## Run deltas` section to `_lane-contract.md` stating that `laneSuite` overrides rule 9's "the full suite at the merge candidate is the conductor's, so don't run it" (`reference/templates/lane-contract.template.md:19`), so a lane reads one instruction, not two; with no `laneSuite`, no section. `record` also refuses (exit 2) when `laneSuite` is set and the file has no `## Run deltas` section. `record` refuses (exit 2) when the file is missing or still contains any `RUN_SLOTS` prefix. At run time the template is read from the installed plugin root, so WP-05's concurrent template edit is not a build-time conflict.
  - **Emitter (D18, D19.15):** each library step returns an array of actions; queue it on `wps[].queue` and emit one per `next`. At emission, fill every argv element that is exactly `{pr.number}`, `{pr.head}` or `{merge.sha}` from the WP record (`--wp release`: from `state.release`); a placeholder whose value is still `null` → `next` exits 2 naming it. Every action id is `<seq>-<step>` with `<step>` from WP-01's `STEPS`; every action the build emits itself carries `step` and `seam` from `STEP_SEAM`. **Waits yield** (D17): `next` returns the oldest live WP's (by `dispatchedAt`) first queued non-`wait` action; if no live WP has one, a dispatch when `dispatchable(state)` is non-empty; only when every live WP is waiting and nothing is dispatchable, a single `wait` with the smallest `waitMs`. A filed blocked touch's read-back is one of these yielding steps (D19.4).
  - **Routing (D19.15, D20):** `record` sends a lane step's result to `recordLaneStep` and a landing step's result to `recordLandStep`, each with a fifth argument `{ exec, read, now }` taken from its own `deps`, applies the returned `patch`, and routes on `outcome`: `continue` → the next queued action or the WP's next step; `amend` → an `author` amendment brief naming `reason` (step `brief`), then a lane `prompt` amendment, WP `amending`, then `wait` and `check` again; `wait` → a yielding `wait`; `done` → the step array ends; `block` → see **Blocked**. A `check` failure re-prompts the lane once with an amendment naming the failed expectation (including a `missing`, `not-exercised` or `vacuous` verdict, D11/D14, D19.23); a second failure blocks the WP.
  - **Shell strings (D18, D19):** the gate command, `WORKIT_SPEND_CMD` and `WORKIT_NOTIFY_CMD` become argv only through `shellArgv(string, deps.platform)` (`lib/exec.mjs`, WP-01). A gate command that is empty, not a command (the template's `human review`), or, on win32, contains `"`, makes that `gate-cmd` step `not-exercised`: no action, one event naming the step and the reason, listed by the analysis. It is never run mis-quoted.
  - **Budget (D16, D19.28):** before each dispatch, with the spend adapter on, a `shell` action (step `spend`) running the string `WORKIT_SPEND_CMD <state.createdAt>`; with it off (unmetered), the lane-only lower bound, the sum of `wps[].lane.costUsd`. At or over `authority.budgetUsd` (only `authority` is read; D19.1) → `dispatchHalt = { reason, since }` and a blocked touch (no `wpId`) whose question carries the number and says `metered` or `unmetered, lane-only lower bound`, with options (a) resume dispatch and (b) end the build.
  - **Dispatch:** for each WP from `dispatchable(state)` (empty while `dispatchHalt` is set): set `wps[].lane.backend` and, when herdr is on but ineligible, `adapters.herdr.detail`, from `chooseBackend(state, deps)` (D18, D19.18); then, in order: `admit` (exec: `[]`); spine `spine_update { questId, currentPhase: 'build' }` (step `flip`; spine on; the pickup flip); lane `create` (fetch, `rev-parse` storing `lane.base`, then the worktree beside the repo, D15.3); `author` the brief from `templates/lane-brief.md` into `wps[].lane.briefPath` (`<run>/lane-<wp-id-lower>.md`, set by the `create` record, D20; step `brief`), linking `<run>/_lane-contract.md`, naming the report path `<run>/lane-<wp-id-lower>-report.md` (both backends, D18), and, when `wps[].runtimeExercise` is empty, asking the lane to name the surface and its check (D18); lane `start`/`prompt`; `wait` (herdr polls at 60 s and yields between polls; the lane deadline is 120 minutes on both backends; D19.17); `check` (WP-02's array, outcome first, D19.16).
  - **Outcome first (D19.16):** `refuted` → WP `refuted` (terminal, `reason` from the report), lane `stop`, and every WP whose `dependsOn` includes it → `deferred` naming it. `stopped: needs conductor` → **Rulings**. `built` → the PR checks, then review.
  - **Rulings before escalation (D19.3, kickoff § Self-recovery):** a lane's `## Needs conductor` asks → an `author` action (step `ruling`): "write `<run>/rulings/<wp-id-lower>-<n>.json` = `{ ruled: '<key>', evidence }` or `{ escalate: true, why }`", where `evidence` is the measurement or file that settles the fork. `record` validates it (`ruled` must be one of the lane's keys and `evidence` non-empty; else exit 2) and appends to `wps[].rulings`. A ruling → an amendment brief carrying the ruling and its evidence (`--no-ruling`, D17), WP `amending`. Only `escalate` opens a blocked touch: `openTouch({ kind: 'blocked', options: <the lane's letters verbatim>, wpId, suspendedStep: 'check' })`, WP `blocked`. A herdr `wait` exit 3 (a pane dialog) opens the same blocked touch with the dialog text.
  - **Review:** `tierFor(wp, changedPaths, contractPaths)` (raises on test files and `contractPaths`, D19.11; applied to every WP, WP-00 included), with `contractPaths` read through `deps.read` from `<intent.repo.path>/.workit/conduct.json` (absent file or key → `[]`; D17) and `changedPaths` from `gh pr diff <n> --repo <o/r> --name-only` (step `review`, part `diff`, recorded by the build itself); then `reviewActions` (T1) or `t2Actions` (T2), with the lane report's uncertainty. `recordLandStep` blocks a managed repo with no codex CLI (D19.12). **Council (D20):** before `t2Actions`' `council_review`, an `author` action (step `council`, part `meta`) writes `<run>/council/<wp-id-lower>/meta.json` = `{ "title": "<WP id>: <WP name>" }`; `record` refuses (exit 2) when the file is missing or its `title` differs. The `council_review` args are the orchestrator's (§ Build scheduling → Council reviews), with `round` the WP's next round and `artifact_paths` the `gh pr diff --name-only` paths. **Zero findings (D20):** a review whose `reviews[]` entry has `findings: 0` skips amendment, adjudication and resolve and goes to `rebaseActions`; `findings: null` is treated as non-zero. Otherwise the findings go to the lane as an amendment brief (`author`, step `brief`); for a council review the conductor authors it from the synthesis, numbering the Critical and Major findings `C<round>-<n>`, and the lane's `## Amendment N` table uses those ids. At the amended report's `check`, `parseAmendmentTable(reportText)` feeds `recordAdjudication` (step `adjudicate`), which queues the reply-body `author` and the `reply` actions; `C<round>-<n>` rows get no reply and no resolve. **Guard rows (D20):** each `conductorRows` entry (verdict `conductor`, slim-review's test-weakening guard) goes through the D19.3 `ruling` step: an `author` action writing `<run>/rulings/<wp-id-lower>-<n>.json` = `{ ruled: 'confirmed'|'refuted'|'judgment', evidence }` or `{ escalate: true, why }`; a ruling → `reply --verdict <ruled> --adjudicator conductor` with its body file; `escalate` → the blocked touch of **Rulings**. Then `resolveThreadActions` for every replied comment id, `judgment` and guard rows included (steps `thread-ids`, `resolve`; D19.9); then `deltaReviewActions` when the amendment changed an **executable line**: any changed file not matching `*.md` (the D19.7 rule; tests and fixtures count, D20); its findings follow the same path. **Every review, delta included, runs before the rebase** (D13.1).
  - **Land (D19.8):** `rebaseActions` when `mergeLockFor(state, wp)` is `free` or `mine` (else a yielding `wait`); its records take the lock and store `rebases[]`. Then the gate command as a `shell` action (step `gate-cmd`) in the WP's worktree at the rebased head (non-zero → amendment; D16); then the `wait` answered by `conduct.mjs land gate --run <run> --wp <id>` (a `shell` action, step `gate`). **`pendingSince` (D18):** the `land gate` record sets `wps[].gate.pendingSince` to `deps.timestamp()` at the first pending result, keeps it across later pending results at the same head, and clears it on a new head or an ok result. Code 6 (pending) → a `wait` (`waitMs` 60000) and `land gate` again; `blocked` → WP `blocked`, "CI did not complete at head"; `staleBase` → `rebaseActions` again (never an amendment); `needsFullReview` → a full review of the rebased head (round + 1), then rebase and gate again; any other failure → amendment naming it (the lock is released). Gate ok and `authority.merge` → `mergeActions` (ending in `land merged --merge-sha {merge.sha}`, filled from the `mergeCommit` record); `merged` code 0 → WP `merged`, lock released; with the notify adapter on, a `shell` action (step `notify`) whose argv is `shellArgv(WORKIT_NOTIFY_CMD, platform)` unchanged and whose `env` is `{ WORKIT_NOTIFY_PR: <pr number>, WORKIT_NOTIFY_SHA: <merge sha>, WORKIT_NOTIFY_REVERT: 'git revert <merge sha>' }` (D20: data rides `env`, never the string), composed once `wps[].merge.sha` is stored; spine `spine_receipt` (completed, the PR as artifact) + `spine_update { workState: 'done', horizon: 'landed' }` (step `receipt`; spine on), except when `questId` is the anchor (depth none/lite): the `completed` receipt only, since the anchor stays open until the showcase answer (D18); lane `stop`. **`land merged` code 5 (D19.8):** `dispatchHalt` set, WP `blocked` ("merged tree differs from the checked head"), and a blocked touch with no `wpId` and options (a) resume dispatch and (b) end the build. Gate ok and no merge authority → WP `held` (`gate` evidence stored, PR open; D12), lock released, lane `stop`.
  - **Blocked (D19.4):** a blocked touch records `wpId` and `suspendedStep`. Spine: one touch filed at a time (D19.2). Its read-back (spine `spine_quest`; core: the touch record's status, read in-process) is a yielding step, `waitMs` 300000, interleaved with other WPs' actions. On an attributed answer to a touch with a `wpId`, the WP goes `blocked → amending` with an amendment brief carrying the answer verbatim (`--no-ruling`, D17), then resumes at `check`; every WP `deferred` because of it returns to `pending`. A blocked touch with no `wpId`: (a) clears `dispatchHalt`; (b) leaves it set. A WP `blocked` with no touch (lane deadline, CI did not complete, herdr wait 1/2, managed without codex, a failed `resolve`) stays blocked and its `reason` is listed.
  - **Deferral (D12, D19):** a pending WP whose `dependsOn` includes a `held` or `refuted` WP → `deferred` with `reason`; a pending WP depending on a `blocked` WP → `deferred` once nothing else is live, and back to `pending` when that WP leaves `blocked`. **Build end:** when no WP is live or dispatchable and no blocked touch with a `wpId` is open, phase → `release`. A blocked touch with no `wpId` that is still open stays open into the showcase (D16).
